## Who should upgrade

* **Everyone who set a Tor proxy in 0.4.0-gamma.1** (the wallet app's Settings, Tor, or `proxy` in `tenerod`): **upgrade now.** In
  0.4.0 the Tor path did not hide what it was meant to hide (below).
* Everyone else: recommended, not required. **Nothing else changes:** the same chain, the same protocol version (3), so 0.4.0 and
  0.4.1 nodes talk to each other, and your wallet and your node's data carry over as they are. Download, close the old app, start
  the new one.

## What 0.4.0-gamma.1 leaked, said plainly, and what is fixed

A tester read the 0.4.0 Tor and Dandelion++ code and found four problems, confirmed one of them with a test, and reported them.
Thank you. All four are fixed, each with a test that fails on the 0.4.0 code.

1. **One identity on both sides (the serious one).** A node showed the **same encryption key and the same handshake number** on
   its direct connections and on its Tor connections. So anyone who met a node both ways could tell it was one node, and tie its
   `.onion` address to its IP address. Most Tor users did not run a `.onion` service, but **with a Tor proxy set (and "Every
   connection through Tor" off) a node reached the seed both through Tor and directly**, so the seed's operator could tie the
   transactions the node sent over Tor to its IP address: the Tor path gave no protection against the peer at its other end.
   **Now** every connection through Tor shows another key and another number, both made new at each start, and nothing a peer can
   ask the node compares the two.
2. **A node's own transaction went to a peer that had connected IN through its `.onion` service.** Such a peer never receives
   anyone else's transactions this way, so it knew the transaction was the node's own. **Now** only peers the node dialled get
   them. (Only nodes with a `.onion` service of their own were affected.)
3. **A peer could fill the Dandelion++ holding area** (1,024 transactions, with no limit per peer), and the node then **announced
   its own next transaction itself**, which names it as the sender. **Now** each peer may hold at most 64 there, all peers together
   1,024 and 32 MiB, and the node's own transactions have 256 places of their own that no peer can take.
4. **A transaction that conflicted with one already waiting** was refused only after its proofs were checked (the most expensive
   check), with no penalty, so one could be sent again and again. **Now** the conflict is looked up first. This was a cost to the
   node (a slow-down), not a leak.

**What these fixes do not change:** Dandelion++ and Tor are still new and unreviewed, and on a network of about ten nodes the
seeds' operator still learns a lot. Tor hides where you connect from, not what you pay (Carrot's and FCMP++'s business,
unaudited), and it hides addresses, not timing. Details: `docs/TOR_PLAN.md`, `docs/DANDELION_PLAN.md`.

## For pool operators

* **`tenero-pool --stats-file PATH`** writes the pool's numbers as a JSON file every 30 seconds, for a web page: its terms, the
  chain height, an **estimated** hash rate, shares, blocks, what is owed and paid, the latest 20 blocks, and each miner **by the
  SHA-256 of its address** (the file lists no address). Nothing new listens on the network. `RUNNING_A_POOL.md`, "The stats file".
* **The pool's block counts and its latest blocks now survive a restart** (a new file, `pool-blocks.dat`, next to the books; the
  books keep their format, so 0.4.0's `tenero-pool` can still open them).

## Check the download before you run it

The files are **not code-signed**, so Windows SmartScreen (and some antivirus programs) will warn about them. **Your antivirus may also
flag these programs as a "coin miner"**: `tenero-miner` is a miner, and nothing mines unless you start it. Check the checksum, or
build from source.

Windows (PowerShell):

    Get-FileHash .\tenero-0.4.1-gamma.1-windows-x64.zip -Algorithm SHA256

Linux:

    sha256sum -c SHA256SUMS --ignore-missing

The result must equal the line for your file in `SHA256SUMS` on this page. The packages are built by a public GitHub Actions workflow
from the tagged commit (`release.yml`); **they are not verified to be bit-for-bit reproducible.**

## What you need, and what was tested

**A node needs about 4.3 GiB of free RAM.** **NVIDIA GPU mining needs an RTX 30 series or newer with a CUDA 13 driver (R580 or newer).**
CPU mining on `gamma` is impractical. The Linux programs need glibc 2.34 or newer (the two window programs 2.35): Ubuntu 22.04 or newer.

* **GPU test status of this build:** passed on the author's RTX 5070 Ti (driver 617.14) on 2026-10-11, on this release's code (the GPU code is unchanged since 0.4.0-gamma.1): the GPU checks 16 of 16, and the mining end-to-end check 2 of 2 (blocks mined on the GPU, verified in full by a CPU node).
* **The test suite** (everything that needs no GPU) passed on the author's PC and in GitHub's CI (Windows and Ubuntu) on the merged
  code; the Python reference too.
* **Not run yet:** the fixed Tor path with a real Tor program on `gamma` (the tests use a stand-in for Tor and the simulator), and
  the AMD backend.

## Honest limits

* **The privacy code is not audited as used** (FCMP++ only partly, Carrot and the code around it not at all); the signatures and
  payment proofs are our own, reviewed by nobody.
* **Dandelion++ and Tor are new and unreviewed**; this release fixes what one careful reader found, and there may be more.
* **The seeds and the pool are the author's** (two machines, one operator). Known flaws: `docs/KNOWN_ISSUES.md`, `docs/THREAT_MODEL.md`.
