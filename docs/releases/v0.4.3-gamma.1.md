**Tenero v0.4.3-gamma.1: the fixes of a security review (18 of its 19 findings), a GPU kernel that mines about 12 % faster on the one card it was measured on, a miner that hands a block in at once, and a wallet-app fix. The same `gamma` chain and the same protocol. An experiment, not a product.**

> **Unaudited. One developer. Nothing on this network has any value. The network can be reset at any time, and your coins on it will be gone when it is.**
> Do not put anything on it that you cannot lose. A stop-mining notice, if one is ever needed, is posted only in the pinned issue:
> https://github.com/zad112/Tenero/issues/1 (only the owner can post there; anything claiming to be a notice anywhere else is not from the project).

> **This is a TEST release. "Released" here means "published for people to try": it does not mean finished, reviewed, audited or safe.**

## Who should upgrade

* **Everyone who runs a node: recommended.** In 0.4.2 one cheap transaction could make every block your node built invalid until a
  restart, and a forged block header could make a node rebuild its 4 GiB dataset (both below, "The security review").
* **Everyone who mines on an NVIDIA card: recommended.** The gathered attempt's kernel is rewritten: about 12 % more attempts a
  second on the author's card (below, "The GPU kernel"), and a found block reaches the node at once instead of up to 200 ms later.
* **Pool operators: recommended.** A miner could make the pool check made-up shares in full, and a crash at the wrong moment could
  pay a round twice.
* **Nothing else changes:** the same chain, the same network protocol (3), so 0.4.0 to 0.4.3 nodes talk to each other, and your
  wallet and your node's data carry over as they are. Download, close the old app, start the new one.

**What you will notice** (each from the review, below): a message signature or payment proof made with 0.4.2 or earlier **no longer
verifies**, and one made now does not verify in an older program (make it again); a node accepts **at most 64 inbound peers** unless
you set `max_inbound` (0 still means no limit); **a new wallet in the app needs a password** (an old password-less wallet still
opens, and can be given one); and the miner's **fee minute is now a fixed minute of the clock**, so a restart neither skips it nor
brings it forward.

## The security review of 2026-10-16

The owner had the whole Rust code read for security problems by an AI assistant. **That is not an audit**, and the reader had
written much of the code it read. It found 19 items; 18 are fixed in this release, each with a test, and the table with every item is
at the end of `docs/THREAT_MODEL.md`. None is a change of the chain's rules. The one left, **item 14** (a block's coinbase may carry 16
outputs and 128 bytes of extra data that weigh nothing, each output a permanent leaf of the tree), **would be a fork of `gamma`** and
waits for the owner's decision. (The list below is in plain words and in its own order; the table has the numbers.)

**Nodes**

* **A transaction whose reference block grew too old stayed in the pool and in every block template**, so every block the node
  built was invalid until a restart. One transaction, valid for one height, did it to every node that took it. **Now** the pool
  refuses one with fewer than 10 blocks left, drops one as soon as it cannot be in the next block, and the template skips one.
* **A forged header on an old parent made a node that holds one dataset free its 4 GiB and build another epoch's** (the cheap
  check costs the forger microseconds at `gamma`'s difficulty). **Now** a side-branch block whose dataset is not held keeps only
  the cheap check; the full checks are made, oldest first, when the branch would become the chain and before anything is undone;
  at most 64 such blocks are held.
* **A stranger who repeated another node's handshake number made this node drop its link to that node.** Two links are one node
  only if they also show the same encryption key, which the peer has proved.
* **No inbound limit by default.** `max_inbound` is now 64 (the owner's decision; 0 still means none), one IP address holds at most
  4 inbound connections, and peers through the node's `.onion` service at most 16 (`max_onion_inbound`); the onion service accepts
  30 connections a minute and pauses when one of its peers earns a ban. Before, every peer through the onion service was a new
  host: no ban held and no per-host limit applied.
* **`.onion` addresses were each their own network group**, so the per-group outbound limit never applied to them. They are one
  group with their own outbound cap (`max_outbound_onion`, 4) and at most 256 in the address book.
* **Every transaction a peer pushed was proof-checked on the reader thread, asked for or not.** Now only transactions this node
  asked that peer for, stem (Dandelion++) transactions within a budget, and none under the minimum fee.
* **A node's pruning height, sent exactly in its hello, tied its onion identity to its IP one.** On a link through Tor it is
  rounded up to a multiple of 1,000. (Direct links keep the exact height: rounded everywhere, a node just behind a pruned peer
  could no longer sync from it, which a simulator test caught.)
* **Honest peers were penalised** for a heavier branch forking below the pruned part, and for a pushed transaction that was only
  stale (an aged reference, a fee under a risen minimum). Neither is held against the peer now.
* **The node's network key (`node.key`) lasted its whole life**, so peers could follow a node from place to place by it. It is
  made new at every start (the file is still written).
* **Bounded sets** (invalid blocks, refused transactions, what each peer knows) were cleared whole when full; they now forget
  their oldest entry.

**Wallets**

* **A message signature or a payment proof's signature was valid on every network for the same keys** (one made on the test
  network held on `gamma`). **Signatures are now version 2**: the challenge binds the network. **Version 1 signatures no longer
  verify**: a signature or a payment proof made with 0.4.2 or earlier must be made again, and one made now does not verify in an
  older program. The Python reference changed with it and the vectors were regenerated (`docs/WALLET_PROOFS.md`). A plain
  payment proof without a signature is unchanged.
* **The wallet app made wallets with no password.** A new wallet, or a changed password, needs one; an older password-less wallet
  still opens and can be given one.
* The wallet's fee was rounded down plus one unit (a fingerprint); it is rounded up.

**The miner's fee**

* **Restarting the miner when its fee minute began skipped the fee.** The fee minute now follows the clock: one fixed minute in
  every 100 (which one depends on the fee's address), whenever the miner was started. It used to be counted from the miner's
  start. The fee itself is unchanged: 1 % of the running time, shown and not switchable (`RUNNING.md`, "The mining fee").

**Pools**

* **A pool miner's share target could drift to 2^255**: half of all made-up mixes then passed the cheap check, each costing the
  pool's node a full check. The share target is never easier than 2^244 (4,096 attempts) unless the block's is; 3 wrong mixes in
  one connection ban the address for 10 minutes; 120 shares a minute per connection (it was 600).
* **A pool crash between sending a payout and saving its books paid the round twice.** Payments are booked and the books saved
  before the node gets them; one the node refuses is owed again; `payments.log` notes both with lines that start with `#`
  (`RUNNING_A_POOL.md`, "The record").
* **The pool's stats gave each miner's last share to the second** to anyone who knows the address. It is rounded to 10 minutes,
  and the pool's log names a miner by its stats key, not its address. `RUNNING_A_POOL.md` now says plainly what anyone who knows
  your address can see on a pool's page.

**Also:** a block template could list more than 8,192 transactions (fixed). **Documented, not changed:** the Dandelion++ secret's
default is a fixed test value (`tenerod` makes its own at every start). One reported item was wrong and nothing was changed for it.

## The GPU kernel: about 12 % more attempts a second, measured on one card

`gather.cu`, the kernel of the gathered attempt (the one `gamma` mines), is rewritten so that an attempt's memory traffic is its
16 MiB of columns alone: the keystream matrix X is now computed from the seed inside the kernel and the fold is done before the
product leaves the registers, where before two helper kernels wrote X and the product to memory and read them back (about 2 MiB
more an attempt, 9 % of the GPU's time). **The result is the same bit for bit**: the GPU self-tests check it against the CPU at the
real parameters and on every slice, and 20 blocks mined through the miner were accepted by the node's CPU check. No chain rule
changes; no vector changes.

**Measured** on the author's RTX 5070 Ti (driver 617.42, the author's memory overclock on), the old and the new build run alternately
in one session, the card otherwise idle (`docs/BENCHMARKS.md`, 2026-10-16 "later"):

| | 0.4.2 kernel | this kernel |
|---|---|---|
| the gathered attempt, benchmark, batch 128 / 256 / 512 | 43,945 to 44,735 attempts/s | **48,954 to 50,240** |
| the miner backend itself (`gpu_mining`), batch 128 / 256 / 512 | 41,343 / 41,454 / 41,369 (earlier the same day) | **48,494 / 49,816 / 50,210** |
| power while it ran | about 256 W | **315 W: the card's limit** |

* **That is one card, one day, one driver.** The same old binary gave 41,100 in the morning and 44,100 an hour later for no known
  reason, so compare runs made in one session, and read the second digit, not the third. **No other card has run this kernel**: the
  machine code for the other NVIDIA generations was built, not run.
* **The card now sits at its power limit** while the kernel runs, so the power limit is part of the ceiling: a card with a lower
  limit, or a hotter one, will see less than 12 %.
* **The first design is about 20 % slower on this kernel** (about 75,000 to about 60,000 attempts a second on the same card),
  because every column tile of an attempt computes X again. **No network the 0.3.0 programs run mines the first design** (`alpha`,
  and `beta` below block 500, are mined by the 0.2.0 programs, which do not have this kernel), so nothing you can mine with this
  release is slower.
* **The AMD backend is not this kernel** (`amd_hip.cpp` is its own code) and is unchanged.
* **Not yet measured:** the real solo miner against a node of this build (about 2 % below the backend before, for the gap at each
  found block), and the kernel on any other card.

## The miner and the node

* **The miner's automatic batch choice** (no `--batch`) measured the first design, about 75,000 attempts a second on the author's
  card, on `gamma`, which mines the gathered attempt at about 41,000 then. It now measures the attempt the chain mines, so the batch
  it picks fits the work it does.
* **A found block is handed in at once.** The solo miner slept out its 200 ms poll before handing a block to the node; it now wakes
  on the backend's channel. The GPU's idle time at each found block went from about 0.3 to 0.45 s to about 0.23 s (measured against
  a node of the earlier build).
* **The node checks a found block's attempt on its 6 dataset threads**: 176.5 ms on one thread, 31.4 ms on six (one attempt, the
  author's Ryzen 9 5900X). **Not a consensus change**: the same arithmetic, tested bit for bit against the one-thread form (2 to
  1,000 threads, both designs); the golden vectors still pin the one-thread form, and the CPU miner keeps it.
* **Tried and not kept:** two batches of gathered attempts in flight on the GPU gave no gain (the attempt is limited by memory
  bandwidth) and would have doubled the batch buffers in video memory.

## Fixed in the wallet app

* **"Synced" is judged against the tip the scan last read**, not a fresh one. When blocks came faster than the window's rebuild
  (several a second on the test rig; one a minute on `gamma`, so there it was rare), the scanned height was always one behind,
  the window kept "catching up" and would not send. The wallet is synced when it has read every block it was told of at its last
  look; a block found since is read at the next tick.

The 1 % miner fee (one minute in every hundred, `gpu` to the project's author, `amd` to its contributor, none for `cpu`; shown on the
screen and in the app, cannot be turned off: `RUNNING.md`, "The mining fee"; only its minute moved, above), the AMD package (**still
not run by anyone on the project**: run its bit-for-bit test first, `AMD_MINING.md`), Dandelion++, Tor, `tenerod peers` and the

## Check the download before you run it

The files are **not code-signed**, so Windows SmartScreen (and some antivirus programs) will warn about them. **Your antivirus may also
flag these programs as a "coin miner"**: `tenero-miner` is a miner, and nothing mines unless you start it. Check the checksum, or
build from source.

Windows (PowerShell):

    Get-FileHash .\tenero-0.4.3-gamma.1-windows-x64.zip -Algorithm SHA256

Linux:

    sha256sum -c SHA256SUMS --ignore-missing

The result must equal the line for your file in `SHA256SUMS` on this page. The packages are built by a public GitHub Actions workflow
from the tagged commit (`release.yml`); **they are not verified to be bit-for-bit reproducible.**

## What you need, and what was tested

**A node needs about 4.3 GiB of free RAM.** **NVIDIA GPU mining needs an RTX 30 series or newer with a CUDA 13 driver (R580 or newer).**
CPU mining on `gamma` is impractical. The Linux programs need glibc 2.34 or newer (the two window programs 2.35): Ubuntu 22.04 or newer.

* **GPU test status of this build:** NOT YET DONE (the author fills this in before publishing: the card, the driver, the date and
  the commit). **The GPU code changed in this release** (the kernel above). On the kernel's own commit (`a834319`, 2026-10-16) the
  GPU self-tests passed on the author's RTX 5070 Ti, driver 617.42 (`gpu_selftest` and `gather_selftest`: the golden vectors, every
  slice, both designs at the real parameters, bit for bit with the CPU), and the mining end-to-end check mined 20 blocks on the GPU
  that a CPU node verified in full, with and without the gathered attempt's fork.
* **The test suite** (everything that needs no GPU) passed in GitHub's CI (Windows and Ubuntu) on the merged code, and the Python
  reference too (374 passed, the 5 known expected failures).
* **Not measured yet:** the review's fixes on `gamma` with real peers (they are tested in the simulator and by unit tests); the
  real solo miner on this build; the new kernel on any card but the author's.

## Honest limits

* **The privacy code is not audited as used** (FCMP++ only partly, Carrot and the code around it not at all); the signatures and
  payment proofs are our own, reviewed by nobody. **The security review above is not a review by anyone else:** it was a reading by
  an AI assistant that had written much of the code, and it found what it found, and an audit by someone else may find more.
* **Dandelion++ and Tor are new and unreviewed.**
* **One finding is open** (item 14, the unweighed coinbase), because fixing it changes the chain's rules.
* **The seeds and the pool are the author's** (two machines, one operator). Known flaws: `docs/KNOWN_ISSUES.md`, `docs/THREAT_MODEL.md`.
