**Tenero v0.3.0-gamma.1: a new network, `gamma`, with FCMP++ and Carrot from its first block. An experiment, not a product.**

> **Unaudited. One developer. Nothing on this network has any value. The network can be reset at any time, and your coins on it will be gone when it is.**
> Do not put anything on it that you cannot lose. A stop-mining notice, if one is ever needed, is posted only in the pinned issue:

> **This is a TEST release. "Released" here means "published for people to try": it does not mean finished, reviewed, audited or safe.** The privacy code in it

## The big change: a new network, `gamma`

**`gamma` is a new chain, not a fork of `beta`.** Fresh genesis (label "tenero gamma network 1", chain id
`bd366b37dc59f25d5d2e15aecd1d5c14810b5c20643f2c0f90384db9ee4c28c4`), **no premine** (the genesis creates no coin), the real proof of work with the **gathered attempt
from block 0**, a starting target of 2^237 (about 524,000 attempts a block), control port **38352** and peer port **38353**. Addresses start **`TENg`**.

* **These programs run `gamma`, `dev` and `test` only. They do not run `beta` or `alpha`.** Keep the 0.2.0 programs for `beta` (its seed on `194.238.27.60` stays up for
  as long as the author keeps it; the `beta` seed and pool on `195.26.244.245` stop when `gamma` starts there). **Nothing moves from `beta` to `gamma`.** Your 24 words
  from a `beta` wallet restore a `gamma` wallet (it starts empty there); a `beta` wallet *file* is refused by these programs, with that advice.
* **Two seeds are built in: `195.26.244.245:38353` and `194.238.27.60:38353`.** Two computers, one person: below the three independent operators `docs/SEED_POLICY.md`
  asks for.
* **One pool is built in: the author's test pool on `gamma`, `195.26.244.245:38335`**, public key
  `4eb53ae8fee5bf1596b3c652896ebf5190c0415d92542c9c536842bd5cfa770a` (pinned by the miner and the app). PPLNS, pays once an hour every miner owed at least 0.1 coins,
  no fee, pays the network's fees itself. **It is one computer run by one person, and it keeps the block rewards: nothing makes it pay.** The app mines alone unless you
  choose a pool.
* **Node, miner, wallet, wallet app, explorer and pool must all be 0.3.0.** The control interface and the pool protocol changed; older programs are refused.

## Privacy: FCMP++ and Carrot

* **FCMP++ (full-chain membership proofs):** a spend proves that the coin it spends is one of **all** the outputs on the chain, not one of 16 as a ring signature does.
  Amounts are hidden by commitments with Bulletproofs+ range proofs. **This is Monero's design and Monero's own Rust code** (monero-oxide), pinned to the exact commit
  Monero's FCMP++ test network uses. **It is only partly audited, and Monero does not run it on its main network yet.**
* **Carrot addresses:** subaddresses, integrated addresses, protection against a sender linking two of your addresses ("Janus"), and view-only wallets. **Written in Rust
  by this project from the specification**, because no Rust Carrot exists; it reproduces Monero's C++ results bit for bit in the tests (keys, addresses, outputs,
  scanning, key images). **Not audited.**
* **Every transaction has the same shape** (outputs in a fixed order, the same small `extra`), a consensus rule, so no wallet's transactions stand out by their form.
* **A small crowd at the start.** A spend hides among the outputs that exist. On a new chain that is none until the first block reward matures (60 blocks), then about one
  more a block, almost all of them rewards of a few miners: **the first spends on `gamma` hide among very few people**, and timing still leaks. The wallet does not warn
  about this yet.

## Signatures and payment proofs: our own, unreviewed

Neither Monero nor the Carrot specification defines message signatures or payment proofs for Carrot yet, so this project composed them from textbook parts
(`docs/WALLET_PROOFS.md`, with an independent Python reference that the Rust matches byte for byte):

* **A message signature** (`TENsig1...`) is a Schnorr proof that the signer knows the two secrets behind an address's spend key.
* **A payment proof** (`TENpay1...`) reveals one output's payment key (its 32-hex-digit "anchor"); the checker rebuilds that one output with Carrot's own sender
  derivations, so the check adds nothing new. A "received" proof also carries the receiving address's signature. A proof shows the amount and the address to whoever
  you give it to.
* **Nobody has reviewed either.** The wallet app and the command line say so wherever they offer them. Spend proofs and reserve proofs are not offered.

## What else is new

* **View-only wallets.** A view key (`TENview1...`, a secret) makes a wallet that **sees and cannot spend or sign**: **view-all** sees incoming and outgoing payments and
  the true balance; **view-received** sees incoming payments only (what was received, not a balance). The wallet app shows an account's view key (Settings, "Show a
  view key…", after the password); `tenero-wallet restore-view` makes the view-only wallet. **The app does not open view-only wallets: only the command line does.**
* **Nodes are pruned by default.** A node keeps the proofs of the last 5,500 blocks only, so its disk grows slowly; `prune_keep = 0` keeps everything (an archive node:
  seeds and the explorer's node should be one).
* **Blocks by weight, and room to grow.** A transaction's proofs weigh a quarter of their bytes. Blocks grow with demand up to 12 MiB of weight (48 MiB of real bytes,
  about 6,300 typical transactions, about 100 a second), but lastingly only with months of real demand (a long-term median, as Monero's). **Worked out from the rules;
  nobody has filled a block of that size.**
* **Fees:** `fee = reward x 1000 x weight / median^2`. A typical payment (2 inputs, 2 outputs) costs about **0.0062 coins** at the start and about 0.00016 at the tail of
  0.5 coins a block (**worked out from the formula, not measured**): about what a `beta` payment cost, for a transaction three times bigger.
* **Compact blocks and compact templates.** A new block travels as its header, reward and transaction ids, filled from the node's pool; a miner on another computer, or a
  pool's miners, get the same compact template and hand a found block back as its header. **Remote and pool miners now mine blocks up to the full ceiling** (the 3 MiB cap
  is gone).
* **Integrated addresses** (your address with a payment ID inside, for a shop or an exchange that must tell payments apart): the app's Receive tab and
  `tenero-wallet integrated-address` make one, and the History tab shows the payment ID of each payment made to one. **Several accounts and subaddresses per
  wallet**, all from the same 24 words.

## Fixed (reported by a tester against `v0.2.0-beta.4`)

* **A node far behind the network banned its healthy peers.** While syncing, it fetched new transactions, judged them against its old chain, called them
  invalid and penalised whoever sent them, until every peer (the seeds included) was banned. It then said "in sync" with no peers, hundreds of blocks
  behind. **Now** a syncing node neither fetches nor judges new transactions (they flow again once it is up to date), a transaction built on a block
  the node does not have yet is set aside unjudged instead of called invalid (on `gamma` every transaction names a recent block, so this matters even
  for a node one block behind), and a node with no peers says "no peers: cannot tell if it is up to date", never "in sync". The tester's own fix for the
  first part, run on `beta` from an empty node to the tip with no bans, is what this follows; on `gamma` it is checked by simulation tests, not yet on
  the real network. **`beta` is not fixed:** it keeps the 0.2.0 programs until it is shut down.
* **Found while fixing that: a peer a block behind was blamed for relaying a transaction already confirmed here.** Now the node remembers the
  transactions of its latest blocks and does not fetch them again, and a transaction whose key image is already spent here is refused without
  penalising the peer that sent it (on its chain it may be valid). Checked by simulation tests. One rarer case is left and written down
  (`docs/KNOWN_ISSUES.md` 16): after a reorganisation 10 or more blocks deep, a relayed transaction can still count against an honest peer.

## Check the download before you run it

The files are **not code-signed**, so Windows SmartScreen (and some antivirus programs) will warn about them. **Your antivirus may also flag these programs as a
"coin miner"**: `tenero-miner` is a miner, and nothing mines unless you start it. Check the checksum, or build from source.

Windows (PowerShell):

    Get-FileHash .\tenero-0.3.0-gamma.1-windows-x64.zip -Algorithm SHA256

Linux:

    sha256sum -c SHA256SUMS --ignore-missing

The result must equal the line for your file in `SHA256SUMS` on this page. The packages are built by a public GitHub Actions workflow from the tagged commit
(`release.yml`); **they are not verified to be bit-for-bit reproducible.**

## What you need, and what was tested

**A node needs about 4.3 GiB of free RAM** (one 4 GiB proof-of-work dataset at a time). **GPU mining needs an NVIDIA RTX 30 series or newer with a CUDA 13 driver (R580
or newer); no CUDA Toolkit.** CPU mining on `gamma` is impractical. The Linux programs need glibc GLIBC FLOOR NOT YET COPIED (from the release workflow's log, "the
oldest glibc the Linux programs need").

* **GPU test status of this build: NOT YET DONE.** The proof of work and the GPU kernels did not change in 0.3.0, but the miner's code around them did (version 3
  templates); the last GPU run was on `v0.2.0-beta.4`'s miner commit.
* **The test suite** (everything that needs no GPU) passed on the author's PC on the final G5 commit, 2026-10-08: **1,140 passed, 0 failed**, 36 skipped (they
  need the GPU or are long runs started by hand). It runs again on the tagged commit in GitHub's CI (Windows and Ubuntu).
* **FCMP++, measured on the author's PC** (Ryzen 9 5900X, one thread, release build): checking 16 to 25 ms an input, 9.4 ms per one-input proof when a block's
  16 are checked together; making a spend's proof 0.5 to 0.9 s for one input, 0.8 to 2.4 s for two (`docs/BENCHMARKS.md`).
* **Run end to end in the tests on one computer:** mining, paying (with real FCMP++ proofs, checked by a node that checks every proof), view-only wallets, signatures
  and payment proofs (every forgery tried was refused), the pool with real sockets, and the wallet app's logic.
* **Not run yet:** anything on the real `gamma` network (it starts with this release), a payment between two people, the pool with more than the author's own miner,
  the Linux wallet app and GPU miner.

## Honest limits

* **The privacy code is not audited as used:** Monero's FCMP++ libraries are only partly audited; this project's Carrot, curve-tree bookkeeping and the code around them
  are not audited at all. **A bug in the tree or the key images could split the chain or allow a double spend**; the tests start there, and they are the author's own.
* **A moving target:** Monero may still change FCMP++ or Carrot before its own main network. `gamma` keeps what it launched with.
* **The signatures and payment proofs are our own construction, reviewed by nobody** (above).
* **The seeds and the pool are the author's** (two machines, one operator). Known flaws are in `docs/KNOWN_ISSUES.md` and `docs/THREAT_MODEL.md`; the plan, its
  decisions and its risks are in `docs/FCMP_CARROT_PLAN.md`.
